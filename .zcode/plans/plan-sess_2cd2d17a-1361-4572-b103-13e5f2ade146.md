## Цель

Изолировать комментарии родительского чата от checkpoint/branch и при этом сохранить комментарии общей части истории там, где SillyTavern сохранил тот же `send_date` слота.

## Подтверждённое поведение SillyTavern

- Checkpoint и branch сохраняют отдельный chat file с копией истории до выбранного сообщения.
- Branch после сохранения сразу открывает новый chat file; checkpoint остаётся в текущем чате и открывается позже.
- При сохранении ST объединяет текущий `chat_metadata` с `{ main_chat: ... }`. Поэтому `chatMetadata.dscomments_commentary.guid` сейчас копируется в новый файл.
- При открытии заполненной ветки ST испускает обычный `CHAT_CHANGED`; отдельного `BRANCH_CREATED` или `CHECKPOINT_CREATED` события нет.
- `CHAT_CREATED` для такой заполненной копии не испускается.
- Обычное переименование чата сохраняет метаданные и должно продолжать использовать тот же GUID/файл.

## Текущая проблема

`feed-file-store.js` принимает скопированный GUID за самостоятельную идентичность нового чата. На `CHAT_CHANGED` он загружает общий `dsc_<guid>.json`, а затем `pruneOrphanedEntries()` сравнивает его с live slots новой ветки. Поэтому возможны:

- общий кэш между parent и branch;
- изменение комментария родителя из ветки;
- удаление parent-only entries при GC ветки;
- повторное повреждение при каждом открытии ветки.

## Рекомендуемая стратегия

### 1. Одноразовая fork-изоляция в server-file store

В `src/feed-file-store.js` добавить распознавание fork/checkpoint до обычного `resolveGuid()`:

- признак чата-копии: непустой корневой `chatMetadata.main_chat` и отсутствие внутреннего маркера обработки;
- если в скопированном metadata уже есть GUID, считать его `inheritedGuid`;
- если GUID отсутствует, это безопасная новая ветка без старого server-file store: mint новый GUID и создать маркер без попытки клонирования;
- если GUID есть, использовать `dsc_<inheritedGuid>.json` только как источник для чтения, но не как новый store.

В metadata DS Comments добавить небольшой служебный маркер, например:

```js
chatMetadata[META_KEY] = {
  guid: newGuid,
  forkHandled: true,
  forkParentGuid: inheritedGuid || null
}
```

`main_chat` сохранить без изменений: он нужен самому SillyTavern для навигации по checkpoint/parent links.

Маркер обязателен, чтобы повторное открытие той же ветки не создавало новый GUID снова. Он также отличает уже обработанную ветку от обычного переименованного чата.

### 2. Безопасное копирование комментариев

При fork-изоляции:

1. Дождаться завершения уже поставленных записей старого store.
2. Прочитать родительский `dsc_<inheritedGuid>.json`.
3. Построить live-key set по текущей скопированной истории.
4. Создать новый mirror только из parent entries, чьи ключи `send_date` присутствуют в новой ветке.
5. Назначить новый GUID и новый `_loadedKey`.
6. Записать новый файл `dsc_<newGuid>.json`, если есть перенесённые entries. Пустой store можно оставить без физического файла до первой записи.
7. Только после этого запускать обычный GC уже на новом mirror.
8. Никогда не запускать GC новой ветки над parent mirror и не удалять parent file.

Политика содержимого:

- общие слоты с тем же `send_date` получают копию комментария;
- новые или перегенерированные в ветке слоты без совпадающего `send_date` начинают без комментария;
- последующие записи и очистка ветки затрагивают только новый файл.

Это сохраняет полезный кэш общей истории, но не делает предположений по индексам сообщений или свайпов. Если SillyTavern при копировании обновил `send_date`, соответствующий entry не переносится и будет создан заново при генерации.

### 3. Надёжность загрузки и записи

Добавить в store:

- экспортируемый `flushFeedStoreWrites()` для ожидания текущей promise-chain перед чтением источника;
- sequence/request guard для `loadFeedStore()`, чтобы медленная загрузка старого чата не перезаписала mirror после более нового `CHAT_CHANGED`;
- сохранение `ctx` и file key в момент постановки write-job, чтобы поздняя смена чата не отправила старую запись в новый файл;
- диагностические события:
  - `event=feed_fork result=detected`;
  - `event=feed_fork result=success|empty|error`;
  - source/new file keys и число перенесённых entries;
  - без текста комментариев.

Существующую последовательность `CHAT_CHANGED` в `src/events.js` сохранить: смена epoch/abort, затем `loadFeedStore()`, затем restore. Вызов fork-изоляции должен быть внутри загрузки store, чтобы branch и checkpoint использовали один lifecycle path.

### 4. Уже существующие ветки, созданные старой версией

Ветка без `forkHandled`, но с `main_chat` и унаследованным GUID будет обработана как legacy fork при первом открытии после обновления:

- текущий общий файл будет прочитан;
- новый GUID будет записан в branch metadata;
- в новый файл попадут только ключи, живые в branch;
- старый общий файл больше не будет изменяться branch-операциями.

Если старый GC уже удалил часть parent entries, восстановить их автоматически нельзя. Это нужно явно задокументировать; новая логика остановит дальнейшее повреждение.

### 5. Startup и обычное переименование

Проверить и покрыть начальную загрузку расширения, когда пользователь уже находится в чате при F5: `loadFeedStore()` должен быть вызван до первого save-mode restore, иначе branch может начать работу с неинициализированным mirror.

Обычный rename не должен считаться fork:

- `main_chat` отсутствует или уже стоит `forkHandled`;
- существующий GUID сохраняется;
- используется прежний `dsc_<guid>.json`.

### 6. Тесты

Добавить в `test/feed-file-store.test.mjs`:

- branch с inherited GUID получает новый GUID и новый file key;
- parent file не изменяется после загрузки/GC branch;
- совпадающие `send_date` entries переносятся;
- parent-only entries не переносятся в branch;
- branch-only/new send dates не получают чужой комментарий;
- повторная загрузка branch не mint-ит новый GUID и не клонирует повторно;
- branch без parent file становится пустым, но не ломает загрузку;
- fork с отсутствующим GUID создаёт marker и не пытается читать случайный файл;
- обычный rename с существующим GUID продолжает использовать старый файл;
- queued parent write завершается до fork-copy;
- stale concurrent load не перезаписывает новый mirror.

Добавить lifecycle-тест в `test/events-lifecycle.test.mjs` или отдельный тест:

- `CHAT_CHANGED` на branch выполняет fork isolation до restore;
- parent и branch получают независимые cache targets.

Существующие migration, GC, deletion, group-chat и no-save тесты прогнать без изменения их контрактов.

### 7. Документация и ручная проверка

Обновить `README.md` и `USER_GUIDE.md`:

- branch/checkpoint создаёт отдельный commentary store;
- общие entries переносятся только при совпадении `send_date`;
- генерация/очистка ветки не изменяет parent;
- checkpoint изолируется при первом открытии, а не в момент создания;
- удаление chat file SillyTavern не перечисляет и не удаляет автоматически server-side `dsc_*.json`.

Ручной чек-лист:

1. Сгенерировать комментарий в parent.
2. Создать checkpoint, продолжить parent, затем открыть checkpoint.
3. Проверить, что общий комментарий виден, но новая генерация в checkpoint не меняет parent.
4. Создать branch и проверить то же сразу после автоматического перехода.
5. Проверить branch с выбранным swipe и branch после перегенерации.
6. Закрыть/открыть parent и branch несколько раз.
7. Повторить для group chat.
8. Проверить rename parent и branch.
